*hexit.txt*  Binary Hex/ASCII editor for Neovim 0.12+       *hexit.nvim*

=============================================================================
INTRODUCTION                                                         *hexit*

Hexit opens an existing regular file as a binary snapshot in a separate
'acwrite' buffer. It reserves one fixed title row for the logical mode, a
Hex-only Byte-column ruler and right-aligned status, above a bounded
Offset/Hex/ASCII viewport; neither the buffer nor the rendering holds a
whole-file text conversion.

Use |:Hex| to open a file; loading Hexit never opens anything by itself.
Opening is a snapshot: changes made to the source by another process are NOT
detected, and |:write| replaces the source with that snapshot.

Hexit has no runtime dependency, does not shell out to `xxd` and does not use
FFI. Neovim 0.12 or newer is required. See |hexit-limits| for what is not
supported.

=============================================================================
INSTALLATION                                                  *hexit-install*

Put this repository in 'runtimepath'; there is nothing to build: >

  vim.opt.runtimepath:prepend('/path/to/hexit.nvim')
<
On an older Neovim the plugin reports an explicit error and registers no
commands. `:helptags doc` from the repository root installs these help tags.

=============================================================================
COMMANDS                                                        *hexit-commands*

:Hex [path]                                                             *:Hex*
                         Open an existing regular file. Without a path, open
                         the current unmodified named ordinary buffer's file.
                         Reopening an active path focuses its Hex buffer.
:HexGoto {offset}        Move to a 0-based Byte offset, decimal or `0x`.
                         Invalid and out-of-file offsets are errors.
:HexCol {width}          Select 8, 16, 32 or auto for this buffer, preserving
                         the logical Byte position and the linewise selection.
:HexSearch {hex|ascii} {pattern}
                         Search forward for exact Bytes or ASCII text; the
                         pattern preserves spaces. See |hexit-search|.
:HexCopyAs [format] [register]
                         Encode the current Byte or the Visual range as text;
                         see |hexit-copy-as|. Completion offers formats first
                         and registers second.
:write                   Save the complete binary document to the source path
                         through a sibling temporary file, fsync, close and
                         rename. A failed write keeps the original file, the
                         dirty state and the history, and `:wq` does not exit.
                         Navigation and viewport movement remain available
                         while saving; editing and undo/redo are frozen. No
                         alternate path, range, append, rename/:saveas or
                         `:w!` semantics, and a Windows replace-rename failure
                         does NOT truncate the source.

=============================================================================
CONFIGURATION                                               *hexit-configuration*

Optional, before opening sessions: >lua
  require('hexit').setup({
    bytes_per_row = 16,       -- 8 | 16 | 32 | 'auto'
    byte_group_size = 1,      -- 1 | 2 | 4, display only
    uppercase_hex = true,
    show_ascii = true,
    show_offset = true,
    default_copy_format = 'hex',
    search_ignorecase = nil,  -- nil reads vim.o.ignorecase at query start
    search_smartcase = nil,   -- nil reads vim.o.smartcase at query start
    mappings = true,         -- true | false | table
  })
<
Unknown fields and invalid values make `setup()` fail; repeated setup affects
sessions opened afterwards only. Mapping tables are copied when setup is called.

`mappings=false` installs the stable `<Plug>(Hexit-{Action})` maps without
default keys or ordinary printable-key protection. During `r`, `R`, and Visual
fill, the temporary data-input layer still captures data keys and `<Esc>`;
ordinary-layer `false` does not change it. Complete combinations
beginning with a captured data key are temporarily shadowed too: ASCII R writes
`,a` as two Bytes even when `,a` is bound to an action. Single r or Visual fill
consumes only its required data; remaining keys are handled normally. Original
single-key and complete-combination mappings are restored when input ends;
global mappings are never modified. Existing native mappings that distinguish
`<Tab>` from `<C-I>` are restored independently.
Hex windows sharing one buffer share one cursor and viewport; the narrowest
window determines auto row width
and the active window controls the visible height. Physical local 'scrolloff'
stays 0 to keep the title fixed, while the saved user 'scrolloff' is kept as a
"logical" viewport margin and restored on leaving (including global
inheritance); setting the local value while in Hex updates both. Pixel-smooth
scrolling, for example in Neovide, is not promised.

=============================================================================
TITLE AND HIGHLIGHTS                                            *hexit-title*

The fixed one-line title has three window-relative parts: the logical mode at
the left, a Hex-only Byte-column ruler in the middle, and right-aligned status.
One blank column precedes the mode and every data row (including offsets), and
one blank column follows the title address. The title has no ASCII ruler, and
the offset/ASCII heading areas carry no labels.

The left side shows `NORMAL`, `VISUAL`, `V-LINE` or `REPLACE`, even when
'show_offset' is false. The ruler writes each Byte-column number at its actual
Hex cell and follows the grouping, bytes-per-row and letter case. The right
side shows, in order, the Visual selection length as `NB` (while selected), the
visible search count (while results are visible), the current area `HEX` or
`ASCII`, and the 0-based Byte address. Nonempty fields are separated by exactly
two spaces; an empty file shows `(empty)`. The address is the current Byte
position, not a range. Each side is positioned relative to its window, and
overlays replace the highlight colors underneath, are not hidden by native
selection or horizontal scrolling, and let the right side win an overlap. Very
narrow windows use Neovim's natural clipping: Hexit never shortens addresses,
hides fields, adds a fallback layout or wraps the title. The title exists even
when 'laststatus' is zero.

Hexit never sets or changes 'statusline', 'winbar' or 'laststatus' and does not
configure lualine; lualine is optional and not a dependency. Neovim 0.12.5's
default statusline `%m` shows `[+-]` for a modified nomodifiable buffer and
`[-]` after a successful save; in a lualine filename component `[+]` means
modified and `[-]` means nomodifiable or readonly, and `[-]` is not a
saved-state marker. The title itself never shows a dirty or save marker.

Default highlight links follow the active colorscheme; set any group directly
to override it. Groups still defined when ColorScheme fires are not
overwritten, so a colorscheme that clears custom groups needs user overrides
reapplied from an autocmd.

  HexOffset -> LineNr              HexOffsetCurrent -> CursorLineNr
  HexOffsetSelection -> Visual     HexHeader -> LineNr
  HexHeaderCurrent -> CursorLineNr HexHeaderSelection -> Visual
  HexHeaderMode -> ModeMsg         HexHeaderStatus -> Normal
  HexByte -> Normal                HexAscii -> Normal
  HexCursor -> Cursor              HexCursorMatch -> MatchParen
  HexModified -> DiffText (dark) / DiffChange (light)
  HexSearch -> Search
  HexSearchCurrent -> CurSearch    HexSelection -> Visual

The dark/light dirty link is chosen at plugin load or ColorScheme rebuilding;
changing only 'background' can keep the existing link, so reapply the
colorscheme to select the other default. An explicit HexModified override is
never replaced by that default. Hex and ASCII data are neutral by default and
the ruler and offsets use line-number colors. In Normal/Replace the current Hex
column and offset share CursorLineNr emphasis, HexCursor marks the active
nibble or ASCII cell, and HexCursorMatch marks the whole Byte in the other area
in every mode, taking priority over Visual on the current Byte only. In
Visual/Visual Line the selected Hex columns and offsets use only Visual, not an
overlapping LineNr foreground that could match its own background; other
selected cells use Visual, with no separate active-cell or column highlight.
Current and other search hits use CurSearch and Search, dirty Bytes use DiffText
on dark and DiffChange on light backgrounds.

KEYS AND PLUG MAPPINGS                              *hexit-keys* *hexit-plug*

Every supported action has a stable buffer-local `<Plug>(Hexit-{Action})`
mapping, installed for all `mappings` settings. With defaults enabled, default
keys only forward to these names.

`mappings` omitted or `true` installs default keys and ordinary printable-key
protection. `false` installs only the `<Plug>` mappings, with no default keys
or protection.

A table enables this default layer unless its reserved `defaults` field is
`false`; if supplied, `defaults` must be boolean and defaults to `true`.
With `defaults=false`, only explicitly configured keys are installed in
addition to the `<Plug>` maps, without ordinary printable-key protection.

Each other table key must be a nonempty string lhs. Its value must be an
existing logical action name from the `<Plug>` action column below (including
`Digit0`–`Digit9`, `GPrefix`, `Unsupported`, `WheelUp`, and `WheelDown`), or
`false`. Internal `CharXX` Plug names protect unsupported
printable keys; they are not configurable actions. Replace data uses a separate
temporary input layer. Arbitrary RHS expressions, functions, and nested mode
tables are not accepted.
Neovim termcodes, including `<leader>`, are resolved at setup. Lhs aliases
that resolve to the same key are rejected.

An explicit action overrides the same-key default, existing user or Plug
mapping, and protection. `false` installs no Hexit mapping and excludes
that lhs from defaults and protection without deleting an existing user map.
It leaves the key to the user's mapping or Neovim fallback, with no promised
Hex behavior. With defaults enabled, adding an alias does not remove its old
default key. Later `FileType` or buffer-local mappings can override Hexit
mappings in the same buffer. Hexit makes no guarantee that mapping a prefix
blocks longer mappings. Explicit bindings use native prefix/timeout resolution;
default core keys retain their immediate mapping priority.
Configuration is copied at setup and applies to new sessions only.

Example: >
  require('hexit').setup({
    mappings = {
      ['<leader>a'] = 'SwitchArea',
      ['<Tab>'] = false,
    },
  })
<
For custom-only mappings, disable the defaults layer: >
  require('hexit').setup({
    mappings = {
      defaults = false,
      ['<leader>h'] = 'Left',
      ['<leader>l'] = 'Right',
    },
  })
<
To keep only the stable `<Plug>` maps without default keys or protection, set
`mappings = false`: >
  require('hexit').setup({ mappings = false })
<

  Key(s)                  `<Plug>` action            Effect ~
  h l k j, arrows         Left Right Up Down         nibble/Byte, row
  w b e                   WordNext WordPrev WordEnd  Byte/word motion
  g g                     GPrefix then First         first Byte
  G                       Last                       last Byte
  0                       Digit0                     row start (no count)
  $                       RowEnd                     row end
  (no default key)        RowStart                   row start
  <C-u> <C-d>             HalfUp HalfDown            half page
  <C-b> <C-f>             PageUp PageDown            full page
  <C-e> <C-y>             Unsupported                silent no-op
  <Tab>                   SwitchArea                 Hex/ASCII area
  v V                     Visual VisualLine          Visual modes
  r R                     Replace ReplaceMode        replace, R mode
  y                       Yank                       binary register
  p P                     PasteAfter PasteBefore     insert register
  u <C-r>                 Undo Redo                  history
  / ?                     SearchForward SearchBackward
  n N                     SearchNext SearchPrev
  <Esc>                   Escape                     clear/hide
  0-9                     Digit0 ... Digit9          counts
  other printable ASCII   CharXX                     unsupported-key protection
  wheel                   WheelUp WheelDown          scroll 3 rows

h/l move nibble by nibble in Hex and Byte by Byte in ASCII; j/k preserve the
preferred Byte column. w/b/e use the original Bytes, not displayed dots. `$`
with a count goes to a later row end, `gg`/`G` with a count select a 1-based
display row. <C-b>/<C-f> keep two rows of overlap. <C-e>/<C-y> are silent
no-ops so the title cannot scroll away. <Tab> keeps the offset and returns to
the Hex high nibble; a hidden ASCII area cannot be entered. A click on a Byte
cell moves the cursor and the wheel scrolls three rows. <Esc> clears count and
prefix, hides completed search results in Normal, leaves Visual, and commits an
active Replace transaction; entering `:` also clears pending navigation input.

Counts are decimal and limited to 2,147,483,647; a rejected count rejects the
whole motion, and `0` without a preceding count is row start. With defaults
enabled, core default keys replace ordinary same-key mappings, unless already
mapped to a Hexit Plug. Protected printable keys leave a complete existing user
mapping alone and allow non-core prefix combinations through native resolution.
Explicit opts mappings override these defaults. `RowStart` has no default
key of its own, so map it when an explicit row-start key is wanted; `g` is
`GPrefix` and a second `g` completes `First`, so counts never depend on mapping
timeouts. Non-core unsupported operations show one native single-line message,
not a notification popup.

=============================================================================
EDITING                                                         *hexit-editing*

v / V     Toggle a Byte or entire-display-row Visual selection. Switching
          between v/V keeps the anchor; motions and <Tab> extend the range.
          The title shows the selection length, and the Hex ruler highlights
          the selected columns and the offsets of actually selected rows;
          Visual has no separate current Byte/column/offset color. Empty files
          cannot select. Visual paste is not supported.
r{digit}  Hex: replace the current nibble; a count repeats the digit over
          consecutive nibble positions. ASCII: replace the current Byte; a
          count repeats one printable ASCII character. Passing EOF rejects
          the whole operation.
Visual r{HH}   Fill the selection with a Hex Byte (exactly two digits).
Visual r{char} Fill the selection with one printable ASCII Byte.
R         Replace Mode: overwrite in place from the current nibble or Byte.
          Input updates both views immediately, crosses row boundaries and
          never grows the document; input after the last Byte is refused.
          Backspace, arrows, <Tab>, page keys, the wheel and mouse clicks do
          not reposition in R. <Esc> commits everything as one undo step.
          Counted R is unsupported. In Hex r/R, `:` opens the native command
          line and commits an active R; in ASCII r/R, `:` writes the literal
          Byte 0x3A, so press <Esc> first when a command is intended.
y         Copy the current complete Byte, or count Bytes truncated at EOF,
          into Hexit's private binary register. Visual y copies the whole
          selection; it does not wait for a second `y`. Use `V y` for a
          display row.
p / P     Insert the binary register after/before the current Byte; in an
          empty file both insert at offset 0. A count repeats the insertion
          as one undo step. System-clipboard paste is not provided.
u / <C-r> Undo/redo counted edits; Visual exits first. Saving does not clear
          history, so undoing a save can mark the buffer modified again.

No partial-Byte file state exists. Modified highlighting compares each current
logical Byte offset with the same offset in the last saved snapshot, so an
insertion can highlight the shifted suffix. Full-content equality, including
manual restoration, clears 'modified' asynchronously; while comparing, the
buffer stays conservatively modified.

SEARCH                                                          *hexit-search*

/ and ?   Enter the real native / or ? command line, with native editing,
          history and |cmdline-completion|. The kind (Hex or ASCII) is
          captured from the current area. An incomplete Hex digit is not
          parsed until <Enter>. Native regex execution is aborted before it
          can touch the rendered buffer or @/. Empty <Enter> repeats the last
          query with the new direction and count, or reports "no previous
          search". <Esc>/<C-c> there abort only the unsubmitted input.
n / N     Next match in the query's direction / in the opposite direction.
          N does not change that direction. A count selects that many
          matches, wraps included; a request reports at most one boundary
          message and a hit may wrap to itself.

Hex patterns accept compact pairs (`89504E47`) or pairs separated by
whitespace (`89 50 4E 47`, `0x89 0x50 0x4E 0x47`). Odd digit counts, commas,
wildcards and regex operators are rejected. ASCII patterns are literal
printable 0x20-0x7E characters, including spaces: `.` and `*` are Bytes here,
not regex operators, so use Hex for 00 and non-ASCII Bytes. Hex searches
ignore case settings; ASCII searches use `search_ignorecase`/
`search_smartcase`, or the corresponding Neovim options captured when the
query starts. With ignorecase and smartcase both on, an uppercase ASCII query
stays sensitive; otherwise folding applies to ASCII A-Z only, and changing the
options later does not alter an existing query.

The right side of |hexit-title| shows `k/total` at a current hit, `0/0` when
counting completed with no matches, `?/?` while counting, or `?/total` when
counting completed without a current hit. A completed zero-result request
shows `hexit: Pattern not found`. A wrap shows
`hexit: search hit BOTTOM, continuing at TOP` or
`hexit: search hit TOP, continuing at BOTTOM` once per request. Both Hex and
ASCII cells of visible matches are highlighted, the current hit distinctly.
Search indexes per 64KiB block, not per hit; editing, undo and redo rebuild a
visible query without navigation or a new not-found message.

Native 'incsearch'/'hlsearch' are suppressed only during Hexit input and are
restored on leaving, including a pre-existing |:nohlsearch| state; unsubmitted
text never triggers a binary preview. Native @/, native n/N, `searchcount()`,
regex syntax and search-offset suffixes do not describe Hexit results. An
invalid submitted pattern shows one native message, while `:HexSearch` parse
errors are command errors. Ordinary buffers keep ordinary / ? behavior.

COPY AS                                                       *hexit-copy-as*

`:HexCopyAs [format] [register]` writes the current Byte or the Visual range
as text with no trailing newline. The Bytes 00 41 7F FF yield: >

  hex       00 41 7F FF
  compact   00417FFF
  escaped   \x00\x41\x7F\xFF
  c         { 0x00, 0x41, 0x7F, 0xFF }
  cstring   "\x00\x41\x7F\xFF"
  python    b"\x00\x41\x7f\xff"
  rust      [0x00, 0x41, 0x7f, 0xff]
  ascii     .A..
  base64    AEF//w==
<
`ascii` is lossy: nonprintable Bytes become `.`. The default format comes from
`default_copy_format`. The default register is the system clipboard `+`; `*`
is also a clipboard and `"` writes the unnamed Neovim text register. A missing
clipboard provider reports an error. Copy As never changes the private binary
register. Large exports stream in 64KiB slices and are cancelled when the
source changes or closes.

STATUS API                                                      *hexit-status*

Public Lua interface: >lua
  local s = require('hexit').get_status(bufnr)
<
An optional external API, not the default display path. A missing or 0 bufnr
means the current buffer; invalid, ordinary and wiped buffers return nil,
otherwise an independent small table rather than a mutable session. The
accessor does not read disk, scan, render or modify options. Fields:

  bufnr, phase                 number; loading/ready/saving/error
  mode, mode_text              normal/visual/visual_line/replace, uppercase
  area, nibble                 hex/ascii; Hex high/low, ASCII nil
  size, offset                 Byte size and 0-based cursor offset; nil before
                               load, and offset is nil in an empty file
  bytes_per_row                actual 8/16/32 once a layout exists
  selection                    nil or { start, stop, length }, [start,stop)
  search                       nil or { kind, direction, visible, pending,
                               ordinal, total }; ordinal is nil when hidden
  input_kind                   nil, or hex/ascii captured while / ? is active
  position_text                "--" unloaded, "(empty)" empty, otherwise 0x
                               plus at least eight address digits
  selection_text               "" or "Sel: N B"
  range_text                   "" or the inclusive displayed start-end (N B);
                               the selection itself stays half-open
  area_text                    HEX HI / HEX LO / ASCII
  search_text                  "" hidden, "searching… ?/?" pending, 0/0 empty,
                               k/total at a hit, ?/total without a current hit

Addresses use the configured Hex case, a fixed `0x` prefix and enough digits
for the file's last Byte. Hexit emits `User HexitStatusChanged` with
`data = { bufnr = N }` after visible status changes, including asynchronous
scan completion and close; notifications are coalesced per event-loop turn, and
reading the snapshot emits nothing. Consumers may build their own integrations
from the snapshot and the event; Hexit itself needs no statusline component,
lualine configuration or refresh callback.

=============================================================================
LIMITATIONS                                                     *hexit-limits*

- No Insert mode (`i`, `a`, `I`, `A`), no delete (`x`, `d`, Visual `p`) and no
  Visual delete.
- No read-only browsing mode, no external-change detection, reload or
  force-write UI, no expression offsets, no named-register integration, no
  automatic binary-file detection, and no ordinary-text/Hex round trip;
  adjusting 'fileformat', 'fileencoding' or reloading the source elsewhere is
  outside Hexit.
- Unsupported edit and operator keys report one native message and never
  change the rendered buffer.
- Search handles exact Byte sequences and printable ASCII literals only: no
  wildcards, regex, multi-encoding or search/replace, and ignorecase folds
  ASCII A-Z only.
- `H`, `M`, `L`, `zt`, `zz`, `zb`, `f`, `F`, `t`, `T`, `;` and `,` are not
  implemented.
- Several windows showing one Hex buffer share one logical cursor and viewport;
  independent per-window scrolling is not supported, while different files use
  independent sessions.
- Copy As only writes text out; system-clipboard paste and paste-from-text are
  not provided.
- `:write` writes the whole document back to the source path only; `:w!`,
  `:w other`, ranges, append and `:saveas` are refused.

Opening is a snapshot and `:write` replaces the target with that snapshot.
External modifications are NOT detected, so do not modify the source file in
another process while Hexit is open, and be aware that a successful `:write`
overwrites whatever the file contains at that moment. Do not run `:write`
concurrently from two Hexit sessions on one path.

The binary snapshot is read asynchronously in 1 MiB chunks and the buffer holds
one title row plus one bounded viewport, so browsing cost does not grow with
file size. Long-running work (search scans, dirty-state comparison, Copy As
encoding) is sliced and yields a real event-loop turn between slices, so input
stays responsive; assembling the final Copy As result text is one un-sliced
step, and a 50 MiB Base64 export builds about 70 MB in roughly 200 ms. Undo
history is an un-limited in-memory piece table: an edit never copies the whole
document, but memory grows with the number of retained entries, so split very
long editing sessions with `:write` and a fresh |:Hex|.
