*hexit.txt*  Binary Hex/ASCII editor for Neovim 0.12+

=============================================================================
INTRODUCTION                                                         *hexit*

Hexit opens an existing regular file as a binary snapshot in a separate
'acwrite' buffer. It reserves one fixed title row for logical mode, a Hex-only
Byte-column ruler and right-aligned status above a bounded Offset/Hex/ASCII
viewport, not a whole-file text conversion. The title has no ASCII ruler.
Use |:Hex| to open a file. Source
files changed by another process are NOT detected. Do not edit the file
elsewhere while using Hexit: |:write| replaces the source snapshot.

Insert, Delete, read-only mode and system clipboard paste are not available
in this checkout. Search supports exact binary Bytes and printable ASCII,
not wildcard or regular-expression patterns. See |hexit-limits| for the full
first-stage scope.

=============================================================================
INSTALLATION                                                  *hexit-install*

Hexit has no runtime dependency and needs no build step. Put this repository
in 'runtimepath': >

  vim.opt.runtimepath:prepend('/path/to/hexit.nvim')
<
Neovim 0.12 or newer is required. On an older Neovim the plugin reports an
explicit error and registers no commands. Loading Hexit never opens a file;
use |:Hex|. `:helptags doc` from the repository root installs these help tags.

=============================================================================
COMMANDS                                                        *hexit-commands*

:Hex [path]              Open an existing regular file; with no path, open the
                         current unmodified named ordinary buffer's file.
                         Reopening an active file focuses its Hex buffer.
:HexGoto {offset}        Move to a 0-based Byte offset in decimal or 0x hex.
                         Invalid/out-of-file offsets are errors.
:HexCol {width}          Select 8, 16, 32 or auto in this buffer; preserve
                         the logical Byte and recompute linewise selection.
:HexSearch {hex|ascii} {pattern}
                         Search forward for exact Bytes or ASCII text.
                         The pattern after the kind preserves ASCII spaces;
                         see |hexit-search|.
:HexCopyAs [format] [register]
                         Encode current Byte or Visual range as text. Default
                         format is `hex`; default register is `+`. Registers
                         `+`, `*`, `"` only. Native command completion offers
                         formats first, registers second; see |hexit-copy-as|.
:write                   Save complete binary document to source path through
                         a sibling temporary file, fsync, close, rename.
                         Failed write keeps original file, dirty state and
                         history. `:wq` fails without exiting if write fails.
                         Navigation and viewport movement remain available
                         while saving; edits and undo/redo are frozen.
                         No alternate path, range, append, rename/:saveas,
                         or `:w!` semantics. Windows replace-rename failure
                         does NOT truncate the original file.

=============================================================================
CONFIGURATION                                               *hexit-configuration*

Optional before opening sessions: >lua
  require('hexit').setup({
    bytes_per_row = 16,       -- 8 | 16 | 32 | 'auto'
    byte_group_size = 1,      -- 1 | 2 | 4, display only
    uppercase_hex = true,
    show_ascii = true,
    show_offset = true,
    default_copy_format = 'hex',
    search_ignorecase = nil,  -- nil reads vim.o.ignorecase at query start
    search_smartcase = nil,   -- nil reads vim.o.smartcase at query start
    mappings = true,
  })
<
Unknown/invalid fields fail. Repeated setup affects new sessions only.
`mappings=false` installs stable `<Plug>(Hexit-{Action})` maps without default
keys; replace input temporarily captures printable keys and restores user
mappings on exit. Hex windows sharing a buffer share one cursor/viewport; the
narrowest window determines auto row width, the active window controls the
visible cursor/page height. Physical local scrolloff=0 keeps the title fixed;
the saved user scrolloff controls the *logical* viewport margin and is
restored on leaving (including global inheritance). Setting local scrolloff
while in Hex updates that margin and the value later restored. No pixel-smooth
scrolling is promised.

=============================================================================
TITLE AND STATUS API                                         *hexit-title*

Hexit keeps its feedback in one fixed title row above the data viewport. The
title has three window-relative parts: logical mode at the left, an underlying
Hex-only Byte-column ruler in the middle, and status information aligned to
the right edge. One blank column precedes the mode and each data row, including
offsets; one blank column follows the title address. Auto row width accounts
for the left margin. The offset heading area and ASCII heading area contain no
title labels or ASCII column numbers. Data Byte columns remain aligned.

The left side shows `NORMAL`, `VISUAL`, `V-LINE` or `REPLACE`. This logical
mode is displayed even when 'show_offset' is false. Neovim's actual mode stays
Normal except during native / ? command-line input. The Hex ruler writes each
Byte-column number at its actual Hex cell; it follows the configured grouping,
bytes-per-row and letter case. The title has no ASCII ruler.

The right side shows fields in this order: Visual selection length as `NB`
(only while selected), visible search count (only while results are visible),
current area `HEX` or `ASCII`, and the 0-based Byte address. Nonempty fields
are separated by exactly two spaces. Addresses use the configured Hex case,
have a `0x` prefix and at least eight digits; an empty file shows `(empty)`.
The address is the current Byte position, not a selection range. Search count
is `?/?` while counting, `0/0` when complete with no matches, `k/total` at a
current hit, or `?/total` when complete without a current hit. Hidden searches
and absent selections contribute no field. The right side remains available
when 'show_ascii' is false.

Each side is positioned relative to its window: the mode starts at window
column one, and the status information uses right alignment with a trailing
blank column, independent of the shared title text, window width and
horizontal scrolling. The mode overlay has priority 80; the right overlay
has priority 100 and wins when they overlap the ruler or mode overlay. Both
overlays replace underlying highlight colors. Very narrow windows use
Neovim's natural clipping; Hexit does not shorten addresses, hide fields,
add fallback layouts or wrap the title. The overlays are not hidden by
native selection or horizontal scrolling.

The title exists even when 'laststatus' is zero. Hexit never sets or changes
'statusline', 'winbar' or 'laststatus', and does not configure lualine. Lualine
is optional and is not a Hexit dependency or a required setup. Neovim 0.12.5's
default statusline uses `%m`: a modified, nomodifiable buffer shows `[+-]`,
and a successfully saved buffer shows `[-]`. In a lualine filename component,
`[+]` means modified and `[-]` means nomodifiable or readonly; both may appear,
and `[-]` is not a saved-state marker. The title never shows a dirty/save
marker.

Default highlight links use Neovim's active colorscheme; set any Hexit group
directly to override its default. Groups still defined when ColorScheme fires
are not overwritten. A colorscheme that clears custom groups requires user
overrides to be reapplied from a ColorScheme autocmd. Defaults:

  HexOffset -> LineNr              HexOffsetCurrent -> CursorLineNr
  HexOffsetSelection -> Visual     HexHeader -> LineNr
  HexHeaderCurrent -> CursorLineNr HexHeaderSelection -> Visual
  HexHeaderMode -> ModeMsg         HexHeaderStatus -> Normal
  HexByte -> Normal                HexAscii -> Normal
  HexCursor -> Cursor              HexCursorMatch -> MatchParen
  HexModified -> DiffText (dark) / DiffChange (light)
  HexSearch -> Search
  HexSearchCurrent -> CurSearch    HexSelection -> Visual

The dark/light dirty link is chosen at plugin load or ColorScheme rebuilding.
Changing only 'background' can retain the existing default link; reapply
your colorscheme to select the other default. Explicit HexModified overrides
are never replaced by that default.

Hex and ASCII data are both neutral by default; the column ruler and offsets
use line-number colors. In Normal/Replace, the current Hex column and offset
share CursorLineNr emphasis. HexCursor marks the active nibble or ASCII cell
outside Visual; HexCursorMatch marks the whole Byte in the other area using
MatchParen's emphasis in both Normal/Replace and Visual. The opposite-area
mark takes priority over Visual selection on the current Byte only. In
Visual/Visual Line, selected Hex columns and actual row offsets use only
Visual, not an overlapping LineNr foreground that could match its background.
Selected Byte cells otherwise use Visual, without a separate active-cell or
current column/offset highlight. Current/other search hits use CurSearch/Search;
dirty Bytes use DiffText on dark backgrounds and DiffChange on light
backgrounds. More prominent marks can cover dirty colors without changing
the modified state. Only real Byte cells are highlighted; the title's mode
and right status replace colors beneath them, with the right status winning
overlaps.

Public Lua interface: >lua
  local s = require('hexit').get_status(bufnr)
<
This remains an optional external API, not the default display path. bufnr
omitted or 0 means current buffer. Invalid, ordinary or wiped buffers return
nil; other calls return an independent small table, not a mutable session.
The accessor does not read disk, scan, render or modify options. Fields and
units:
  bufnr, phase                 number; loading/ready/saving/error
  mode, mode_text              normal/visual/visual_line/replace and uppercase
  area, nibble                 hex/ascii; Hex high/low, ASCII nil
  size, offset                 Byte size and 0-based cursor offset; both nil
                               before load; empty offset nil
  bytes_per_row                actual 8/16/32 when a layout exists
  selection                    nil or { start, stop, length }, [start,stop)
  search                       nil or { kind, direction, visible, pending,
                               ordinal, total } (hidden => ordinal nil)
  input_kind                   nil or captured hex/ascii while / ? is active
  position_text                "--" unloaded, "(empty)" empty, otherwise
                               0x plus at least eight address digits
  selection_text               "" or "Sel: N B"
  range_text                   "" or inclusive displayed start-end (N B);
                               internally selection remains half-open
  area_text                    HEX HI / HEX LO / ASCII
  search_text                  "" hidden, searching… ?/? pending, 0/0 empty,
                               k/total at a hit, ?/total without current hit

Addresses use the configured Hex case, a fixed 0x prefix and enough digits
for the file's last Byte. Hexit emits `User HexitStatusChanged` with
`data = { bufnr = N }` after visible status changes, including asynchronous
scan completion and close; notifications are coalesced per event-loop turn.
Reading the snapshot does not emit the event. External consumers may use the
snapshot and event to build their own integrations; Hexit itself needs no
statusline components, lualine configuration or refresh callback.

MOVEMENT                                                          *hexit-keys*

The actual Neovim mode stays Normal except during native / ? command-line
input. Hexit maintains logical Normal, Visual, Visual Line, and Replace modes,
shown in the title (see |hexit-title|). Counts are decimal,
limited to 2,147,483,647. `0` without a count is row start. `Esc` clears
count and prefix; in Normal it also hides completed search results.

h/l, Left/Right    Hex: nibble-by-nibble; ASCII: Byte-by-Byte.
j/k, Up/Down       Row motion, preserving preferred Byte column through EOF.
w/b/e              Hex: Byte/low-nibble motion; ASCII: word/space/punctuation
                   runs determined from original Bytes, not displayed dots.
0/$                Current row start/end; counted `$` goes to later row end.
gg/G               Beginning/end; count specifies 1-based display row.
Ctrl-u/d           Half-page up/down based on active window height.
Ctrl-b/f           Full page up/down with two rows of overlap.
Tab                Switch Hex/ASCII at same offset; returning Hex chooses high
                   nibble. Hidden ASCII cannot be entered.
Mouse              Click a Byte cell to move; wheel scrolls three rows.
Ctrl-e/y           Silent no-op to keep the title at the top.

Core keys take precedence over ordinary same-key mappings; protected
non-core printable keys do not replace existing complete user mappings
and wait for multi-key mappings such as <leader>w. If the leader is itself
a core key, explicitly remap the desired action using its Hexit Plug mapping.
For example, a FileType hexit autocmd can take over h after attachment: >lua
  vim.api.nvim_create_autocmd('FileType', {
    pattern = 'hexit',
    callback = function(args)
      vim.keymap.set('n', 'h', '<Plug>(Hexit-SwitchArea)',
        { buffer = args.buf, remap = true })
    end,
  })
<
An explicit RHS can still attempt unrelated native operations; Hexit does
not replay or reinterpret user mappings. Non-core unsupported operations
display one native single-line warning, not a notification popup.

=============================================================================
PLUG MAPPINGS                                                    *hexit-plug*

Each supported action has a stable buffer-local `<Plug>(Hexit-{Action})`
mapping. Default keys, when `mappings` is true, only forward to these names:

  Key(s)                        `<Plug>` action              Motion/effect ~
  h l k j, <Left> <Right>       Left Right Up Down           nibble/Byte, row
  <Up> <Down>
  w b e                         WordNext WordPrev WordEnd    Byte/word motion
  g g                           GPrefix then First           first Byte
  G                             Last                         last Byte
  0                             Digit0 (no count)            row start
  $                             RowEnd                       row end
  <C-u> <C-d>                   HalfUp HalfDown              half page
  <C-b> <C-f>                   PageUp PageDown              full page
  <Tab>                         SwitchArea                   Hex/ASCII area
  v V                           Visual VisualLine            Visual modes
  r R                           Replace ReplaceMode          replace, R mode
  y                             Yank                         binary register
  p P                           PasteAfter PasteBefore       insert register
  u <C-r>                       Undo Redo                    history
  / ?                           SearchForward SearchBackward search prompt
  n N                           SearchNext SearchPrev        match navigation
  <Esc>                         Escape                       clear/hide
  0-9                           Digit0 ... Digit9            counts
  other printable ASCII         CharXX (Char41 is "A")      r/R data input
  wheel                         WheelUp WheelDown            scroll 3 rows
  <C-e> <C-y>                   Unsupported                  silent no-op

Counts and `gg` do not use timeout-dependent overlapping mappings: `g` is
GPrefix and a second `g` completes First. A default key is skipped when the
buffer already maps it, so user mappings win; a `FileType hexit` buffer-local
mapping to a `<Plug>(Hexit-...)` name replaces the default. With
`mappings=false` only the `<Plug>` names are installed; `r`/`R` still install
their temporary data keys and restore the user's mappings on exit.

=============================================================================
SEARCH                                                          *hexit-search*

/ / ?              Enter the *real* native / or ? command line. The kind
                   (Hex/ASCII) is captured from the current area; native
                   editing and search history work. An incomplete Hex digit
                   is not parsed until Enter. Native regex execution is
                   aborted before it touches rendered text or @/. Empty
                   Enter repeats the last query with the new direction and
                   count; with no query, reports "no previous search".
                   Esc/Ctrl-C here abort only the unsubmitted input.
n / N              Next match in the query's direction / opposite direction.
                   N does not change that direction. Counts select that many
                   matches, including multiple wraps; a request reports at
                   most one boundary message. One hit can wrap to itself.
Normal Esc         Hide count and matches, cancel scans/navigation, but keep
                   last query for n/N. Visual Esc exits selection without
                   hiding completed results; R Esc commits its transaction.

Hex patterns accept compact pairs (`89504E47`) or pairs separated by
whitespace (`89 50 4E 47`, `0x89 0x50 0x4E 0x47`). Odd digits, wildcards,
commas and regex operators are rejected. ASCII patterns are literal
printable 0x20–0x7E characters, including spaces: `.` and `*` are Bytes,
not regex operators. Use Hex for 00 or non-ASCII Bytes. Hex searches ignore
case settings; ASCII searches use `search_ignorecase` and `search_smartcase`
or the corresponding Neovim options captured when the query starts. With
ignorecase and smartcase enabled, an ASCII uppercase query stays sensitive;
otherwise folding applies only to ASCII A–Z. Changing options later does
not alter the existing query.

The right side of the |hexit-title| shows the match's ascending Byte-offset
ordinal and total (`k/total`), `0/0` when counting is complete with no matches,
`?/?` while counting, or `?/total` when complete without a current hit. A
completed zero-result request displays
`hexit: Pattern not found` via the native message line. Forward/reverse
wrap displays `hexit: search hit BOTTOM, continuing at TOP` or
`hexit: search hit TOP, continuing at BOTTOM` once per request. Both Hex
and ASCII cells of visible matching Bytes are highlighted; the current hit
has a distinct color. Overlaps are valid. Search indexes per 64KiB block,
not per hit. Editing/undo/redo rebuild a visible query without navigation
or an extra not-found message. A hidden query stays hidden until n/N or
explicit search.

Native `incsearch`/`hlsearch` are temporarily suppressed only during Hexit
input and restored on leaving, including an existing :nohlsearch state.
Unsubmitted text does not trigger binary preview. Native @/, native n/N,
searchcount(), regex syntax and native search-offset suffixes do not describe
Hexit results. An invalid submitted pattern shows a single native message;
Ex :HexSearch parse errors remain command errors. Ordinary buffers retain
ordinary / ? behavior.

=============================================================================
SELECT AND EDIT                                             *hexit-editing*

v / V    Toggle Byte or entire-display-row Visual selection. Switching between
         v/V retains anchor. Motions and Tab extend the range; Esc exits Visual
         without hiding completed search. Selection length appears in the title.
         The Hex ruler highlights selected columns and offsets of actual
         selected rows; Visual has no separate current Byte/column/offset color.
         Empty files cannot select.
r{digit}  Hex: replace current nibble, count repeats digit over consecutive
         nibble positions. ASCII: replace current Byte, count repeats one
         printable ASCII character. Beyond EOF rejects the entire operation.
Visual r{HH}  Fill selection with a Hex Byte (exactly two hex digits).
Visual r{char}  Fill selection with one printable ASCII Byte. One undo step.
R        Replace Mode: overwrite in place from the current nibble/Byte. Input
         updates both views immediately, crosses row boundaries, never grows
         the document; after the last Byte, further input is refused.
         Backspace, arrows, Tab, page keys, wheel and mouse clicks do not
         reposition in R. Esc commits all changes as one undo step.
         Counted R is unsupported.
         In Hex r/R, `:` opens the native command line and commits active R.
         In ASCII r/R, `:` writes the literal Byte 0x3A; press Esc first
         when a command is intended.
y        Copy current complete Byte or count Bytes, truncated at EOF, into
         Hexit's private binary register. Visual y copies the whole selection.
         It does not wait for a second `y`; use V y for a display row.
p / P    Insert the binary register after/before the current Byte; in an empty
         file both insert at 0. Count repeats insertion once as one undo step.
         Visual paste is unsupported. System clipboard Paste is not provided.
u / Ctrl-r  Undo/redo counted edits. Visual exits first. Saved history remains
            available: undoing a save may mark the buffer modified again.

No partial Byte file state exists. Modified highlighting compares each current
logical Byte offset with the same offset in the last saved snapshot; inserted
Bytes and a shifted suffix can be highlighted. Full-content equality (including
manual restoration) clears 'modified' asynchronously; while comparing, the
buffer remains conservatively modified. History is not limited and may consume
more memory as edits accumulate.

=============================================================================
LIMITATIONS                                                    *hexit-limits*

This checkout implements the first-stage scope only:
- No Insert mode (`i`, `a`, `I`, `A`), no delete (`x`, `d`, Visual `p`), and
  no Visual delete.
- No read-only browsing mode, no external-change detection, reload or
  force-write UI, no expression offsets, no named-register integration, no
  automatic binary-file detection, and no ordinary-text/Hex round trip.
  Adjusting 'fileformat', 'fileencoding' or reloading the source in another
  process is outside Hexit.
- Unsupported edit and operator keys report one native message and never
  change the rendered buffer.
- Search handles exact Byte sequences and printable ASCII literals only: no
  wildcards, no regular expressions, no multi-encoding, no search/replace.
  Ignorecase folds ASCII `A`-`Z` only.
- `H`, `M`, `L`, `zt`, `zz`, `zb`, `f`, `F`, `t`, `T`, `;` and `,` are not
  implemented.
- Several windows showing one Hex buffer share one logical cursor and
  viewport; independent per-window scrolling is not supported. Different
  files use independent sessions.
- Copy As only writes text out. System-clipboard Paste and Paste From Text
  belong to a later stage.
- `:write` writes the whole document back to the source path only; `:w!`,
  `:w other`, ranges, append and `:saveas` are refused.

Opening a file is a snapshot and `:write` replaces the target with that
snapshot. External modifications are NOT detected, so do not modify the
source file in another process while Hexit is open, and be aware that a
successful `:write` overwrites whatever the file contains at that moment.
Do not run `:write` concurrently from two Hexit sessions on one path.

Undo history is kept in memory without a limit, so memory grows with the
number of edits; see |hexit-performance|.

=============================================================================
PERFORMANCE                                               *hexit-performance*

The binary snapshot is read asynchronously in 1 MiB chunks and the buffer
only ever holds one title row plus one bounded viewport, so browsing cost does
not grow with the file size. Searching keeps per-64KiB-block counts instead of
a per-hit list, which is why a 50 MiB file full of `00` reports 52,428,800
matches without allocating a table per hit.

Editing history is a piece table: every edit stores only piece references, so
an edit never copies the whole document, but each retained undo entry keeps
its piece array. Measured on Windows 10.0.26200 x64 with Neovim 0.12.5 after
10,000 single-Byte edits on a 50 MiB document: p95 edit latency 8 ms, the
piece table stayed at 51 pieces, the Lua heap reached ~100 MB, and process
RSS grew ~1.9 GB (mostly allocator retention, not live Lua data). Long editing
sessions on very large files should be split with `:write` and a fresh |:Hex|.

=============================================================================
COPY AS                                                      *hexit-copy-as*

Use `:HexCopyAs [format] [register]` on the current Byte or selected range.
Output has no trailing newline. The bytes 00 41 7F FF yield: >
  hex       00 41 7F FF
  compact   00417FFF
  escaped   \x00\x41\x7F\xFF
  c         { 0x00, 0x41, 0x7F, 0xFF }
  cstring   "\x00\x41\x7F\xFF"
  python    b"\x00\x41\x7f\xff"
  rust      [0x00, 0x41, 0x7f, 0xff]
  ascii     .A..
  base64    AEF//w==
<
`ascii` is lossy: nonprintable Bytes display as `.`. `+`/`*` require a system
clipboard provider; `"` writes the unnamed Neovim text register instead.
Copy As never changes the private binary register. Large exports stream in
64KiB slices and are cancelled when the source changes or closes.
